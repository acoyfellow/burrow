# v5 review 2, round 3: correctness and cost

Scope: `git show 3e9de47` and `git show e0f33da`, plus the current `src/thread.ts`, `src/directory.ts` and `src/loop.ts`. I also checked `src/agent.ts` to see which tools exist and how they run (`executionMode`).

## Status of round-2 H1: FIXED (the unbounded part is gone)

- `thread_send` now throws from a looping thread (src/thread.ts:441-442). The `create` + `send` bypass is closed for the looping thread itself.
- `start()` → `assertOwnerBudget` (src/thread.ts:679-693) now applies to every turn, whoever starts it: user, loop, `thread_send`, `thread_create` task or `start_child`. It refuses when `workingFor(owner) >= 8` and when `spendFor(owner) >= $25`. `spendFor` now adds $0.50 for each busy row (src/directory.ts:185-194).
- `thread_create` is capped at 40 agent-made threads per owner (src/directory.ts:196-205, src/thread.ts:670-673). The per-thread counter now goes up before the await (src/thread.ts:668), which closes round-2 M2.
- Tree fan-out (20 → 400 → 8000) is now bounded. Agent tools run `sequential` (src/agent.ts:234, 269, 278), and `target.start` awaits `publish` with busy=true before it returns. So each creator adds at most one working thread per tool call, and the 8-working cap plus the $25 cap stop the tree. The worst case is a few extra concurrent turns past the cap, and every one of them is checked at start. That makes the spend bounded, not unbounded.

## Medium

- **M1. src/thread.ts:377-397 (`start_child`) skips every new cap except the ones in `start()`.** It is not blocked for looping threads. It does not touch `childrenMade`. It sets `createdBy: 'agent'`, which does not match `agentThreadsFor`'s `LIKE 'thread:%'` (src/directory.ts:200), so it never counts toward the 40-thread cap. A loop turn can call `start_child(task)` on every run, and that child spend never shows up in `loop.startedCost`/`maxSpend` (src/loop.ts:58). The 8-working and $25 checks in `start()` still apply, so total spend is bounded by the owner cap plus overshoot, but `maxSpend` doesn't protect anything here. Each child also takes a snapshot and gets its own computer. Fix: route `spawn` through `assertChildBudget(owner, true)` and count `'agent'` rows in `agentThreadsFor`.
- **M2. src/thread.ts:701-708 + src/directory.ts:185-194. The reserve and working count only see a turn after `submit`.** `busy=true` is set and published only after `assertOwnerBudget`, `open`, `markTurn` and `submit` (src/thread.ts:697-712). Starts that run concurrently on different threads (several creators, several loop alarms) all pass `workingFor < 8` and the reserve check before any of them publishes. Overshoot is bounded by how many starts can run at once (the working creators plus the looping threads), but the "at most 8" promise is not exact.
- **M3. The $0.50 reserve is not a ceiling.** Caps are checked only when a turn starts (src/thread.ts:681-693, src/loop.ts:56-59). Nothing aborts a turn already running. Up to about 8 concurrent turns can each spend far more than $0.50, so actual spend can end up well over $25 (8 × one turn's cost). This is bounded but larger than one turn. Carried over from round 2 M3.
- **M4. src/thread.ts:1188-1192 + 1210-1214. Stop can still be followed by one stray turn.** `loopStep` sets `ledger.loop = next` and then awaits `start()`. `start()` has awaits of its own (`assertOwnerBudget`, `open`, `markTurn`) before `submit`, and it never re-checks `loopStillCurrent`/`loopId`. If `stop()` runs in that window, `agent.stop()` happens before `submit`, so one paid turn runs after Stop. It is one turn and the loop stays disabled. Round-2 M1 is unchanged. Fix: pass the `loopId` into `start` and re-check it right before `submit`.
- **M5. src/thread.ts:681. `assertOwnerBudget` still returns early when `ledger.owner` is empty.** Legacy or ownerless threads have no working cap and no spend cap. `assertChildBudget` then runs `spendFor('')`/`agentThreadsFor('')` against the shared empty owner.
- **M6. src/thread.ts:1167-1169. A failed gate exec still maps to exit 1** and burns another run. Carried over.
- **M7. src/thread.ts:447. `thread_send` checks `busy` and then starts (check-then-act)**, so two senders can submit to the same target at once. Carried over from round 2 M4.

## Low

- **L1. src/thread.ts:668. `childrenMade` is incremented before the checks that can throw** (owner thread cap, spend cap). Failed attempts use up the per-thread quota. This fails safe.
- **L2. src/directory.ts:237 + src/thread.ts:691.** The owner cap is the sum over rows that still exist. Deleting threads (which the error message suggests) removes their spend, and deleting agent-made threads resets the 40 count. Only the owner can do this, so it is not an agent bypass, but the cap is not a lifetime cap.
- **L3. src/loop.ts:70-80.** The digest counts spend on this thread only. The busy-wait branch is still dead code.
- **L4. src/thread.ts:1124-1133.** `loopId` closes round-2 L1 for new loops. Legacy loop states have `loopId` undefined, and two of them would compare equal. This is harmless after the next restart.
